A. BDA stores into writable device heap mirrors (correctness).
   Evidence: run 3b4b885f, 77 x "[gpu] deferred write-back failed: BDA access failed ... reason=2; the
   store hit 0x1210000000+0xab000000, read-only in the BDA table" at about 280 s (instructions 0x84 and
   0x1a8, 4-byte compute stores spread across the 2.87 GB mirrored heap). A faulting dispatch loses its
   whole write-back (Recorder.cpp completion catch).
   Fix: ShaderInfo::bdaWrites (already computed in ResourceTracker.cpp) is carried into
   CompiledShaderArtifact::bdaWrites (Recompiler.hpp/.cpp, ShaderDiskCache.cpp encode/decode,
   FormatVersion 25 -> 26). ShaderAddressResources.cpp calls new
   GuestBufferMemory::AddAddressWritableMirrors() after AcquireRegistered for programs with bdaWrites;
   it notes every writable device-local heap mirror (>256 MiB only when the bounded stream threshold
   applies) in Writes(), which grants BDA Write and routes it through the exact bounded write-back.
   Opt-out: APS5_NO_BDA_MIRROR_WRITES=1.
   Known cost: each such dispatch takes a full-range snapshot + compare (about 1 s for 2.87 GB with B).
   Watch [heap-writeback-snapshot] frequency once loading is reached.

B. Bounded snapshot reuse (performance).
   Evidence: run 3b4b885f, 15 snapshots of the same 2.87 GB heap, identical partition (stored
   462,094,336 / uniform 2,406,809,600), capture_ms 0.8-7.8 s (about 53 s of a 75 s window) while the
   matching completion read-back takes about 0.5 s: the cost was the synchronous unbuffered spool write.
   Fix: HeapWritebackSnapshot::Recapture (byte-exact compare against the retained spool, rewrites only
   changed mixed blocks, refuses uniform->mixed so the caller takes a fresh snapshot). GuestBufferMemory
   keeps the last completed snapshot per (mirror, offset), max 2 entries, taken exclusively and returned
   only after a finished compare. New static ReleaseRetainedSnapshots(). Opt-out APS5_NO_SNAPSHOT_REUSE=1.
   Log line now has reuse=fresh|reused|layout_changed rewritten_bytes=N.

3. THE THREE STEPS FOR CODEX
=====================================================================
STEP 1 - Measure (no game launch needed beyond one diagnostic run if a dump is required).
  Add a census of live host imports, printed with the memory ledger (and once at guard stop if possible):
  - group the 7719 imports by registered guest range (GuestAllocations range / dmem file), with total
    bytes, count, min/max window size;
  - per range: CPU write activity (write-watch / heap-refresh dirty blocks over time), GPU access kind
    (read-only binding vs written), time since last GPU use, whether it is a texture/RT/buffer source;
  - also break down the remaining ~5.3 GiB of non-import working set (IR, caches, file-backed dmem pages
    touched by the CPU, staging pools).
  Deliverable: a ranked table showing which few ranges hold most of the 5.4 GiB and which are read-mostly.

STEP 2 - Move the biggest read-mostly ranges to VRAM, one range first.
  Mechanism to build on (already in GuestBufferMemory.cpp): device-local heap mirrors
  (APS5_DEVICE_HEAP_MIRRORS / acquireMirror / planSpaceMirrors), CPU dirty tracking with per-64 KiB
  generations (prepareRefresh, refreshHeapRuns, [heap-refresh] lines), and exact GPU write-back
  (round-8 change A + bounded snapshots B). After a range is served by a VRAM mirror, release its host
  import (unpin) and let Windows trim the guest pages (they are file-backed dmem, so they can go to disk;
  existing --trim-source-range / --trim-refresh-source-range paths).
  Selection policy must be explicit and stable (by measured range, not by eviction under pressure):
  the handover's failed experiment was pressure eviction of small windows, which caused immediate
  re-import churn because address-space construction re-imports everything broadly registered.
  Budget: VRAM headroom about 6.6 GiB; device-local allocations charge commit (commit_available was
  3.8-5.5 GiB at stops), so cap the moved total and log it.
  Tests first: exactness for CPU writes after upload, GPU writes (declared and BDA), aliasing views,
  sparse/uncommitted pages, and that a moved range is not re-imported by the next address-space build.

STEP 3 - Validate in game.
  Same launcher and settings (work/research/round7_test_warm_game.py, 512 MiB reserve), same
  shader-cache state. Compare against run 07b3d75f at equal RenderFrameIndex: working set,
  imported_host MiB, VRAM usage, commit_available, FPS. Success = working set lower by >= 2 GiB at the
  same frame and the run reaches the loading phase (snapshots / post-1100 frames). Then check whether
  change A removes the "read-only in the BDA table" faults and whether the guest gets past the
  post-intro transition.
